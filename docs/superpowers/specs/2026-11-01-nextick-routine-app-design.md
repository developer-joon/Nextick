# Nextick 설계 문서

- 작성일: 2026-11-01
- 상태: 사용자 최종 검토 대기
- 화면 시안: `docs/superpowers/specs/mockups/2026-11-01-nextick/` (전체: `00-all-screens.html`, ① ~ ㊻)

표기 규칙: **[사용자]** 는 사용자가 결정한 내용, **[제안]** 은 대화 중 설계자가 제안했고 사용자가 반대하지 않은 내용, **[설계자 판단]** 은 이 문서를 쓰며 정한 내용이다. 표시가 없는 항목은 위 결정에서 바로 따라 나오는 내용이다.

## 1. 의도

여행을 준비하다 보면 "출국 며칠 전에 비자 신청, 여권 만료 확인"처럼 해야 할 일과 시기가 이미 정해져 있다. 그런데 이걸 직접 정리해서 일정으로 등록하는 건 번거로워서 안 하게 된다.

Nextick은 **남이 만들어 둔 루틴을 골라서 내 날짜만 넣으면, 해야 할 때 iPhone과 Apple Watch로 알려주는 앱**이다. "만들기"가 아니라 "찾아서 따라 하기"가 주인공이다.

## 2. 목표 / 비목표 / 실패 기준

### 목표

- 허브에서 루틴을 골라 날짜만 넣으면 바로 시작된다.
- 여러 루틴을 동시에 진행한다. [사용자]
- 정해진 때에 푸시가 오고, 알림에서 바로 완료 처리한다.
- 사용자가 루틴을 올리고, 공유하고, 댓글을 달고, 작성자를 팔로우한다. [사용자]
- 첫 사용자가 없어도 허브가 비어 보이지 않도록 공식 루틴과 작성 가이드를 함께 제공한다. [사용자]

### 첫 버전 비목표

- Android [사용자]
- 유료 판매, 결제, 정산 [사용자]
- 앱 안의 단어 퀴즈 (나중에 검토) [사용자]
- 작성자가 임의의 외부 API 주소를 등록하는 기능 [사용자]
- k8s 매니페스트, 배포, 도메인 등록 (사용자가 직접 수행) [사용자]
- 앱스토어 제출 작업 자체 (제출 가능한 상태까지만 준비) [설계자 판단]
- 다국어 지원 범위: **미정** (12장)

### 이렇게 되면 실패다

- 루틴을 시작할 때 입력할 게 많아서 "내가 직접 만드는 것"처럼 느껴진다.
- 알림이 늦거나, 같은 알림이 두 번 오거나, 지운 루틴의 알림이 계속 온다.
- 앱스토어 심사에서 사용자 제작 콘텐츠 관리 기능이나 계정 삭제 부재로 거절된다.
- 저작권이 있는 단어 자료를 공식 루틴에 넣는다.
- 광고가 루틴 시작, 완료 체크, 알림 확인 흐름을 방해한다.

## 3. 사용자가 정한 방식

- 앱: Swift, SwiftUI로 iPhone 앱과 Watch 앱을 함께 만든다.
- 서버: TypeScript(Node.js)로 직접 만든다. Firebase, Supabase 같은 관리형 백엔드는 쓰지 않는다.
- 푸시: 서버에서 APNs로 보낸다. 기기 로컬 알림 예약을 쓰지 않는다.
- 전달물: Dockerfile을 포함해 GitHub 저장소 `developer-joon/Nextick`에 올린다. 사용자가 k8s에 배포하고 도메인을 등록한다.
- 로그인: Apple, 카카오, 네이버, Google.
- 디자인: 새로 창작하지 않고 Structured / 위젯 카드 스타일을 참고한 다크 테마 컬러 카드(시안 C).
- 외부 데이터: 공식으로 연결한 데이터 소스만 쓴다.
- 수익 모델: 첫 버전부터 AdMob 광고를 넣는다. 앱 ID는 `ca-app-pub-2281035356217685~4498098800`이다.

## 4. 핵심 개념

**루틴 = 일정 + 항목 + 완료 버튼 문구** [제안]

| 일정 종류 | 작성자가 정하는 것 | 사용자가 시작할 때 넣는 것 | 끝나는 시점 | 예 |
|---|---|---|---|---|
| 기준 날짜형 | 단계별 D-n | 기준 날짜, 알림 시간 | 기준 날짜가 지나거나 전부 완료 | 여행, 이사 |
| 주기형 | 주기, 총 횟수 | 시작일, 알림 시간 | 마지막 회차가 지나거나 전부 완료 | 적금 120회 |
| 목록형 | 항목 목록, 하루 개수, 보내는 방식 | 시작일, 알림 시간, 하루 개수, 보내는 방식 | 항목 소진 | 영어 단어 |

- **템플릿(허브 루틴)** 과 **내 루틴(사본)** 은 분리한다. 허브에서 받으면 사본이 만들어진다. 작성자가 원본을 수정하거나 삭제해도 진행 중인 내 루틴은 바뀌지 않는다. 새로 받는 사람에게만 새 내용이 적용된다. [제안]
- 알림 모양은 모두 같고 내용과 버튼 문구만 다르다. [제안]
- 버튼 문구("외웠어요", "환전했어요")는 작성자가 루틴을 만들 때 정한다. 루틴 기본 문구(㉚ ㉛ ⑱)가 있고, 기준 날짜형은 단계별로 ㉜에서 덮어쓸 수 있다. 아무것도 정하지 않으면 "완료"다. 알림 버튼, ㉑ 알림 상세, 루틴 상세, Watch가 같은 문구를 쓴다. 받는 사람도 ④에서 내 사본의 문구를 바꿀 수 있다. [설계자 판단]
- 보내는 방식은 "항목마다 알림"과 "하루 한 번 묶음"이다. 작성자가 기본값을 정하고 받는 사람이 바꿀 수 있다. [제안]
- 항목마다 알림일 때 같은 날 항목들은 시작 시간부터 일정 간격으로 나눠 보낸다. 간격 기본값은 30분이다. [설계자 판단]
- 알림 하나가 완료 하나다. "항목마다 알림"이면 항목별로, "하루 한 번 묶음"이면 그날 묶음 전체를 한 번에 완료한다. 달성률은 완료한 알림 수 / 전체 알림 수다. [설계자 판단]
- 작성자의 "주기"는 간격이고, 실제 날짜는 받는 사람의 시작일을 기준으로 정한다. 매월 31일처럼 없는 날은 그달 말일로 보낸다. [설계자 판단]
- ⑯의 "500,000원"처럼 사람마다 다른 값은 별도 입력 항목을 두지 않는다. 시작할 때 입력을 늘리지 않기 위해, 내 사본의 문구를 수정해서 넣는다. [설계자 판단]
- 내 루틴에서 고칠 수 있는 범위 [설계자 판단]
  - 공통: 이름, 시작일 또는 기준 날짜, 알림 시간
  - 기준 날짜형: 단계 추가, 삭제, 순서 변경, D-n
  - 주기형: 주기, 총 횟수, 문구
  - 목록형: 하루 개수, 보내는 방식. 항목 하나하나는 고치지 않는다.

## 5. 화면

시안 번호 기준이다. 숫자와 닉네임은 전부 예시 데이터다.

- ① 로그인: 4개 소셜 로그인. 처음이면 자동 가입된다. 이용약관에 동의한다. [제안]
- ② 홈: 진행 중인 루틴 카드. + 는 허브로 이동한다.
- ③ 상세: 단계별 D-day와 체크. ••• 메뉴에 수정, 삭제, 허브 공유.
- ④ 수정, ⑤ 삭제 확인.
- ⑥ 허브: 검색, 카테고리, 인기순.
- ⑦ 허브 루틴 상세, 가져오기: 시작에 필요한 값만 묻는다.
- ⑧ 내 루틴을 허브에 공유: 단계와 D-day 간격만 올린다. 내 날짜와 체크 기록은 올리지 않는다. [제안]
- ⑨ 히스토리: 끝난 루틴, 달성률, 다시 하기.
- ⑩ Watch: 알림에서 완료·미루기, 오늘 할 일.
- ⑪ 댓글, ⑫ 신고·차단, ⑬ 작성자 프로필.
- ⑭, ⑮ 영어 단어 알림: 앱을 열지 않아도 단어, 뜻, 예문이 보인다.
- ⑯ 루틴별 알림 비교.
- ㉒ 약관 동의, ㉓ 알림 권한 안내, ㉔ 빈 홈, ㉕ 목록형 상세, ㉖ 주기형 상세, ㉗ 중단된 루틴, ㉘ 신고 사유, ㉙ 작성 가이드.
- ㉚ 기준 날짜형 만들기, ㉛ 주기형 만들기, ㉜ 단계 설정.
- ㊸ 전체 카테고리, ㊹ 항목 하나 추가, ㊺ 한 번에 넣기.
- ㊻ 광고 추적 안내.
- ㉝ 히스토리 상세, ㉞ 내 정보, ㉟ 프로필 수정, ㊱ 알림 설정, ㊲ 내가 올린 루틴, ㊳ 팔로잉, ㊴ 차단 목록, ㊵ 자료 출처·문의, ㊶ 회원 탈퇴, ㊷ 오프라인·오류.
- ⑰ ~ ⑲ 루틴 만들기 3단계: 종류, 항목과 기본값(표 붙여넣기 지원), 설명과 공개.
- ⑳ 워크플로우 설정: 데이터 고르기, 값 뽑기, 쓸 곳 정하기.
- ㉑ 알림 상세: 알림을 누르면 열리는 화면. 워크플로우 값을 보여준다.

㊱의 방해 금지 시간, 댓글 알림, 새 팔로워 알림은 설계자 제안이다. 사용자가 원하지 않으면 뺀다. 방해 금지 시간에 걸린 알림은 시간이 끝나면 바로 보낸다. [설계자 판단]

## 6. 동작 규칙

### 카테고리

- 처음에는 20개로 시작한다: 여행, 건강·운동, 식단·다이어트, 마음·수면, 돈·저축, 투자·재테크, 공부·어학, 시험·자격증, 일·커리어, 습관·자기계발, 이사·집, 생활·집안일, 결혼·가족, 육아, 반려동물, 자동차, 명절·기념일, 취미, 서류·행정, 기타. [사용자 요청, 목록은 설계자 제안]
- 목록은 서버에서 관리해서 앱 업데이트 없이 추가할 수 있다. 루틴 하나는 카테고리 하나에 속한다. [설계자 판단]

### 목록 입력

구분 기호를 직접 쓰게 하지 않는다. [사용자 피드백 반영]

- 작성자는 먼저 형식을 고른다: 단어장(단어, 뜻, 예문), 문장(문장, 설명), 운동(운동, 횟수), 직접(칸 이름 지정). 형식에 따라 입력 칸이 정해진다.
- 항목은 ㊹에서 하나씩 넣거나 ㊺에서 한 번에 넣는다.
- 한 번에 넣기는 메모나 엑셀에서 복사한 내용을 붙여넣으면 탭, 쉼표, `|`를 자동으로 인식해 칸을 나눈다. 빈 값과 중복만 표시해서 고치게 한다.
- 파일 업로드는 첫 버전에 넣지 않는다. [설계자 판단]

### 시작과 수정

- 알림 시간은 사용자가 시작할 때 정하고, 기기의 시간대를 함께 저장한다. [설계자 판단]
- 지금 시점에 이미 지난 단계는 "지난 단계"로 표시하고 알림을 보내지 않는다. 몰아서 보내지 않는다. [설계자 판단]
- 날짜나 시간을 바꾸면 아직 끝나지 않은 단계의 발송 일정을 다시 계산한다.
- 삭제하면 남은 알림을 취소하고, 완료한 기록은 히스토리에 남긴다. [제안]

### 완료와 미루기

- 완료는 앱, 알림 버튼, Watch 어디서든 가능하다. 네트워크가 없으면 기기에 보관했다가 나중에 서버로 보낸다. 같은 완료를 두 번 보내도 결과는 같다.
- 미루기는 Watch 시안대로 다음 날 같은 시간에 다시 보낸다. [설계자 판단]
- 완료하지 않은 단계는 다시 알리지 않는다. 다음 단계는 예정대로 진행한다. 목록형도 안 외운 단어가 있어도 다음 날 다음 항목으로 넘어간다. [설계자 판단]
- 모든 단계를 끝냈거나 일정이 끝나면 히스토리로 옮긴다. 달성률은 완료 수 / 전체 수다. [제안]
- 목록형의 연속 기록(🔥)은 하루에 한 개 이상 완료한 연속 일수다. [설계자 판단]

### 허브와 커뮤니티

- 모든 루틴은 무료다. [사용자]
- 직접 만든 루틴은 먼저 내 루틴으로 저장되고, ⑲에서 "허브에 공개"를 켰을 때만 올라간다. ⑧ 공유는 ⑲를 재사용한다. [설계자 판단]
- 받은 루틴을 다시 공유하면 원작자를 함께 표시한다. CC BY-SA 자료의 출처 표시 조건도 사본에 유지한다. 내 사본은 원본 템플릿을 참조로 가진다. [설계자 판단]
- 정렬은 인기순과 최신순이다. 인기는 다운로드 수 기준이다. [설계자 판단]
- 좋아요, 다운로드 수, 팔로워 수를 보여준다.
- 팔로우한 작성자가 새 루틴을 공개하면 푸시로 알린다. 내 정보에서 끌 수 있다. [제안]
- 닉네임은 가입 때 자동 생성하고 내 정보에서 바꾼다. 소셜 계정의 실명, 이메일은 공개하지 않는다. [설계자 판단]
- 공식 계정 "Nextick 공식"의 루틴에는 공식 표시를 한다.

### 광고 [사용자]

- 첫 버전부터 iPhone 앱에 AdMob 광고를 넣는다. Watch 앱과 푸시 알림에는 넣지 않는다.
- 위치는 ⑥ 허브 목록과 ⑨ 히스토리 목록 사이의 네이티브 광고 카드다. "광고" 표시를 분명히 하고, 앱 카드와 구분되게 한다. [설계자 판단]
- 로그인, 약관, 루틴 상세, 시작, 만들기, 완료 체크, ㉑ 알림 상세, 신고, 탈퇴 화면에는 넣지 않는다. 앱 시작 광고와 전면 광고는 쓰지 않는다. [설계자 판단]
- 개인 맞춤 광고를 위해 iOS 추적 동의를 받는다. 첫 루틴을 시작한 뒤 ㊻을 보여주고 iOS 동의 창을 띄운다. 거절해도 기능은 같고 비개인화 광고가 나온다. [설계자 판단]
- 해외 사용자가 받을 수 있으므로 Google UMP 동의 절차를 넣고, ㉞에서 광고 설정을 다시 열 수 있게 한다. [설계자 판단]
- 광고를 없애는 유료 상품은 넣지 않는다. 모든 기능은 광고 동의와 무관하게 쓸 수 있다.
- 개발과 테스트 빌드에서는 Google 테스트 광고만 쓴다. 자기 광고를 눌러 검증하지 않는다.
- 앱스토어 개인정보 항목, 개인정보처리방침, 연령 등급에 광고 내용을 반영한다.

### 앱스토어 심사 대응 (필수)

- 사용자 콘텐츠 신고: 루틴, 댓글, 사용자.
- 사용자 차단: 차단한 사용자의 루틴과 댓글이 보이지 않는다.
- 이용약관 동의 없이는 콘텐츠를 올릴 수 없다.
- 관리 수단: 신고 목록 조회, 콘텐츠 숨김, 사용자 정지. 첫 버전은 관리자 키로 보호한 API만 제공하고 관리 화면은 만들지 않는다. 신고 확인은 운영자(사용자)가 맡는다. [설계자 판단]
- 공개는 즉시 된다. 사전 심사는 없고, 금칙어 필터가 루틴과 댓글을 먼저 거른다. 앱과 약관에 운영자 연락처를 공개한다. [설계자 판단]
- 규정 위반으로 숨겨진 루틴은 이미 받은 사본의 남은 알림도 중단하고 "운영 정책으로 중단됨"으로 표시한다. 작성자가 직접 지운 경우에는 계속 진행된다. 작성자를 차단해도 이미 시작한 내 사본은 유지한다. [설계자 판단]
- 앱 안에서 회원 탈퇴가 가능하다. 탈퇴하면 개인 데이터를 삭제하고 Sign in with Apple 토큰도 해지한다. 공개한 루틴은 "탈퇴한 사용자" 표시로 남기고, 댓글은 삭제한다. [설계자 판단]

### 공식 데이터 연결

- 서버에 미리 구현한 연결(커넥터)만 쓴다. 작성자는 "오늘의 환율" 같은 값을 골라 문구에 넣는다. [사용자]
- 발송 몇 분 전에 미리 받아 저장한다. 같은 데이터는 한 번만 받아 재사용한다. [제안]
- API가 실패하면 최근 값을 쓰고, 최근 값도 없으면 작성자가 정한 기본 문구로 보낸다. 내용이 빈 알림은 보내지 않는다. [제안]
- 첫 버전의 공식 데이터는 환율과 날씨다. [사용자] 제공처는 구현 계획 단계에서 상업적 이용, 저장, 호출량 조건을 확인한 뒤 고른다.
- 응답 값을 뽑아 쓰는 방법은 다음 절의 워크플로우를 따른다.

### 워크플로우 [사용자]

루틴 알림이 울릴 때, 공식 데이터의 응답에서 특정 값만 뽑아 쓰는 기능이다.

```text
공식 데이터 가져오기 → 값 뽑기 → 조건 확인(선택) → 알림 문구 또는 알림 상세에 쓰기
```

- 항목(단계)마다 워크플로우를 하나 붙일 수 있다. 없어도 된다. [설계자 판단]
- 작성자는 코드를 쓰지 않는다. 샘플 응답을 보고 필드를 눌러 고르고, 이름을 붙인다. 값은 문구에 `{{환율}}`처럼 넣는다. 저장 형식은 필드 경로다. [설계자 판단]
- 쓸 곳은 두 가지다. 알림 제목·본문, 그리고 ㉑ 알림 상세. 잠금화면에 다 담기 어려운 내용은 상세에 넣는다. [사용자]
- 기록을 남긴다. 알림이 나갈 때의 값을 저장해서, 나중에 ㉑이나 히스토리에서 그때 값을 볼 수 있다. [설계자 판단]
- 임의의 주소 호출, 스크립트 실행, 작성자 API 키 입력은 허용하지 않는다. 대상은 서버에 등록된 공식 데이터 소스뿐이다. [사용자]
- 서버는 저장 시 필드 경로가 해당 데이터 소스에 있는지 검사한다. 푸시 본문은 APNs 크기 제한을 넘지 않도록 잘라내고, 상세는 앱이 서버에서 받아 표시한다.
- 값이 비어 있으면 공식 데이터 연결의 실패 규칙을 그대로 따른다.
- 조건부 알림: 숫자 값의 이상, 이하 조건을 하나 붙일 수 있다. 예: 환율이 1,350 이하일 때만 보내기. [사용자, 범위는 설계자 판단]
  - 조건에 맞지 않으면 그 알림을 "건너뜀"으로 기록한다. 건너뛴 알림은 달성률과 연속 기록 계산에서 뺀다.
  - 데이터를 받지 못해 조건을 판단할 수 없으면 최근 값으로 추측하지 않고 건너뛴다. 건너뜀 사유를 기록한다.
  - 조건이 있는 알림은 작성 화면에 "조건에 맞을 때만 알려요"로 표시한다.
- 데이터 소스, 추출 규칙, 추가 조건은 허브 공유 대상이다. 사본에는 규칙만 복사되고, 값은 서버가 발송 때마다 새로 받는다.

## 7. 시스템 구성

```text
iPhone / Watch ──HTTPS──▶ API 서버 ──▶ PostgreSQL ◀── 푸시 워커 ──▶ APNs ──▶ iPhone / Watch
                             │                            │
                             ▼                            ▼
                    소셜 로그인 검증                  공식 데이터 소스
```

### 저장소 구조 [설계자 판단]

```text
ios/       Xcode 프로젝트: iPhone 앱, Watch 앱, 알림 확장
server/    API 서버, 푸시 워커, Dockerfile, DB 마이그레이션
content/   공식 루틴 원본 (CC BY-SA 단어 자료 포함)
docs/      설계 문서, 작성 가이드
```

### 서버

- 같은 이미지를 환경변수로 API 또는 워커로 실행한다. k8s에서 각각 별도 Deployment로 띄울 수 있다. [설계자 판단]
- DB는 PostgreSQL이고 `DATABASE_URL`로 받는다. DB 설치는 사용자 몫이다.
- 비밀값은 전부 환경변수로 받고, `server/.env.example`에 목록을 둔다.
- `/healthz`, `/readyz`를 제공한다. 로그는 표준출력으로 내보낸다. SIGTERM을 받으면 처리 중인 작업을 끝내고 종료한다.
- 마이그레이션은 별도 명령으로 실행한다. 사용자가 k8s Job이나 init container로 돌릴 수 있게 하고, 실행 방법을 문서화한다.

### 푸시 발송

- 루틴을 시작하면 각 단계의 발송 시각을 계산해 발송 예정 행(row)으로 저장한다.
- 워커는 매분 도래한 행을 가져가 APNs로 보낸다.
- 워커를 여러 개 띄워도 중복 발송이 없어야 한다. PostgreSQL 행 잠금(`FOR UPDATE SKIP LOCKED`)으로 한 행은 한 워커만 처리하고, APNs `apns-collapse-id`로 재시도 시 중복 표시도 막는다.
- APNs가 토큰 무효를 알리면 해당 기기 토큰을 삭제한다. 일시 오류는 제한된 횟수만큼 재시도한다.
- 워커가 잠시 멈췄다가 살아나면 밀린 알림을 보낸다. 단, 일정 시간(기본 6시간) 이상 지난 알림은 보내지 않는다. [설계자 판단]
- 사용자 한 명이 여러 기기를 쓰면 모든 기기로 보낸다. Watch는 iPhone 알림 미러링을 기본으로 한다. Watch 앱은 iPhone과 같은 계정 상태를 쓴다.

### 구현 순서의 시작 [사용자 답변 반영]

유료 Apple Developer 계정, APNs 키, 실제 iPhone과 Apple Watch가 이미 있다. 따라서 가장 위험한 부분을 먼저 검증한다.

1. 서버에서 보낸 푸시가 실제 iPhone과 Watch에 오는지 확인한다.
2. 루틴별 버튼 문구가 잠금화면과 Watch에 나오는지 확인한다.
3. Watch에서 누른 완료가 서버에 기록되는지 확인한다.

이 결과로 버튼 문구 방식을 확정한 뒤 나머지를 만든다.

### 구현 시 주의 (기술 제약)

- **iOS 알림 버튼은 푸시 내용만으로 지정할 수 없다.** 버튼은 앱이 미리 등록한 알림 카테고리로 정해진다. 루틴마다 버튼 문구가 다르므로, 알림 서비스 확장이나 앱 동기화 시점에 카테고리를 등록하는 방식이 필요하다. 첫 구현 단계에서 실제 기기로 검증한다. 안정적으로 되지 않으면 ⑱의 자유 입력을 정해진 문구 목록(완료, 확인했어요, 납입했어요, 외웠어요, 했어요) 선택으로 바꾼다. [설계자 판단]
- **Watch에서 누른 완료 처리**가 iPhone 앱을 거치는지, Watch 앱에서 처리되는지 실제 기기로 확인하고 구현한다.
- Sign in with Apple은 다른 소셜 로그인을 제공하므로 반드시 포함한다. 탈퇴 시 토큰 해지를 위해 서버에 Apple refresh token을 저장한다.

### 로그인

앱이 각 공급자 SDK로 받은 토큰을 서버로 보내면, 서버가 공급자에 검증하고 자체 토큰(access + refresh)을 발급한다. 같은 사람의 다른 소셜 계정을 하나로 합치는 기능은 첫 버전에 넣지 않는다. [설계자 판단]

## 8. 초기 콘텐츠

- 작성 가이드: `docs/guides/routine-authoring.md`. 앱의 허브에서 볼 수 있게 연결한다. [사용자]
- 공식 예시 루틴 3개: 해외여행 준비, 10년 내집마련 적금, 영어 단어. 가이드에 쓴 방식 그대로 만든다. [사용자]
- 영어 단어는 허브의 무료 공식 루틴이다. [사용자]

### 영어 단어 자료

| 자료 | 용도 | 조건 |
|---|---|---|
| [NGSL](https://www.newgeneralservicelist.com/new-general-service-list) | 필수 단어 2,809개, 빈도순 | CC BY-SA 4.0 |
| [TOEIC Service List](https://newgeneralservicelist.com/toeic-service-list) | 토익 어휘 (후속 후보) | CC BY-SA 4.0 |
| [Tatoeba](https://tatoeba.org/ca/downloads) | 예문 | CC BY 2.0 FR, 문장별 라이선스 확인 필요 |

- 첫 공식 루틴은 NGSL에서 300개를 고른다. 목록이 빈도순이라 맨 앞은 the, be, and 같은 단어이므로 앞부분을 그대로 쓰지 않고, 학습 가치가 있는 구간을 고른다. 시안 ⑭의 단어는 예시다. [설계자 판단]
- 위 자료에서 한글 뜻을 확인하지 못했으므로 AI로 초안을 만들고 사용자가 직접 검수한다. 검수가 끝나기 전에는 공개하지 않는다. [사용자] 예문의 한글 번역도 같은 방식이다. Tatoeba 문장별 라이선스를 확인할 수 없는 예문은 쓰지 않는다. [설계자 판단]
- 만든 단어 목록은 CC BY-SA 4.0으로 `content/`에 공개하고, 앱의 자료 출처 화면에 출처를 표시한다.
- 토익 단어장과 Oxford 3000은 쓰지 않는다.
- 단어는 알림마다 API로 가져오지 않는다. 한 번 만들어 저장하는 제작 과정으로 처리한다. [사용자]

```text
NGSL 단어 선택 → AI로 뜻과 예문 초안 → 사용자 검수 → content/에 저장 → 공식 루틴으로 등록
```

- 번역 API는 결과 저장과 재사용 조건을 약관에서 확인한 뒤에만 쓴다. 알림마다 API를 호출하는 방식은 환율, 날씨처럼 값이 바뀌는 공식 데이터에만 쓴다.
- 시안 ⑥의 "토익 필수 단어 30일"은 예시일 뿐이다. 실제로는 이 자료 조건을 따른다.

## 9. 유럽(EU) · 영국 출시 [사용자]

출시 국가에 EU와 영국을 포함한다. 아래는 법률 자문이 아니다. 출시 전에 전문가 확인이 필요한 항목은 따로 표시했다.

### 앱과 서버에서 구현할 것 [설계자 판단]

- **광고 동의:** EU·영국 사용자는 Google UMP 동의를 받기 전에 광고를 요청하지 않는다. 동의를 거절하거나 철회해도 모든 기능을 쓸 수 있다. ATT와 UMP를 함께 쓸 때 동의 창 순서는 Google 안내를 따른다.
- **개인정보 최소 수집:** 소셜 로그인에서 받은 이메일과 실명은 저장하지 않는다. 계정 연결에 필요한 공급자 사용자 ID만 저장한다. 서버 로그에는 IP와 토큰 원문을 남기지 않거나 짧게 보관한다.
- **내 데이터 받기:** ㉞ → 약관·개인정보 화면에서 내 데이터(루틴, 기록, 댓글, 팔로우, 차단)를 JSON 파일로 받는다. 열람권과 이동권 대응이다.
- **회원 탈퇴:** 6장 규칙대로 삭제하고, 백업에서 지워지는 기간을 개인정보처리방침에 적는다.
- **나이 확인:** 가입할 때 만 16세 이상인지 확인한다. 16세 미만이면 가입하지 않는다. EU 국가별 동의 연령의 최댓값에 맞춘 단순 기준이다. 이것만으로 영국 Online Safety Act의 "아동이 접근할 가능성이 없다" 판단이 충분하지 않을 수 있으므로 전문가 확인 항목에 포함한다.
- **콘텐츠 조치 통지:** 운영 정책으로 루틴이나 댓글을 숨기면 작성자에게 사유를 알리고, 앱에서 이의 제기를 할 수 있게 한다(㊲의 "사유 보기"에 이의 제기 버튼). 신고, 조치, 이의 제기 기록을 보관한다. EU DSA의 통지·사유 제공 의무에 대비한다.
- **비회원 신고:** 웹 주소 하나로 로그인 없이 불법 콘텐츠를 신고할 수 있게 한다. 앱 밖 사람의 신고를 받는 창구다.
- **지역 표시:** 날짜, 시간, 숫자 형식은 기기 지역 설정을 따른다. 시간대는 이미 루틴별로 저장한다.
- **공식 데이터:** 환율은 EUR, GBP를 포함하고, 날씨 제공처는 유럽 도시를 지원해야 한다. 제공처를 고를 때 EU·영국 상업 이용 조건을 함께 확인한다.
- **로그인 버튼 순서:** 기기 지역이 한국이 아니면 Apple, Google을 먼저 보여주고 카카오, 네이버는 아래에 둔다.

### 사용자가 할 것

- **App Store Connect DSA 판매자(trader) 신고:** 광고 수익이 있는 앱이므로 판매자로 신고하는 것이 맞을 가능성이 크다. 판매자로 신고하면 주소, 전화번호, 이메일이 EU 앱스토어 페이지에 공개된다. 개인 주소가 공개되지 않게 하려면 사업자 주소나 사서함을 준비한다.

## 11. 검증 기준

- 서버: 일정 계산(3종, 시간대, 지난 단계, 날짜 변경), 중복 발송 방지, 재시도, 토큰 무효 처리, 탈퇴, 차단, 신고를 자동 테스트로 확인한다. 실제 PostgreSQL로 통합 테스트를 돌리고, 워커 2개를 동시에 띄운 중복 발송 테스트를 포함한다.
- Docker: 이미지를 빌드하고 컨테이너로 실행해 `/readyz`가 성공하는지 확인한다.
- iOS: 뷰 모델과 오프라인 완료 큐를 단위 테스트한다. iPhone과 Watch 빌드가 성공해야 한다.
- 실제 기기 확인: 푸시 수신, 잠금화면 버튼, Watch 완료 처리는 구현 첫 단계에서 사용자의 기기로 확인한다. 키 파일은 저장소에 넣지 않는다.
- EU·영국: 기기 지역을 EU·영국으로 바꿨을 때 UMP 동의 전 광고 요청이 없는지, 내 데이터 받기와 이의 제기가 동작하는지 확인한다.
- 광고: 테스트 광고가 ⑥ ⑨에만 나오고, 동의 거절과 광고 로드 실패 때도 화면과 기능이 정상인지 확인한다.
- 조건부 알림: 조건 충족, 미충족, 데이터 실패 때 발송과 건너뜀 기록, 달성률 계산을 자동 테스트로 확인한다.
